# Frontend roadmap

Status: **all nine slices shipped** (see `README.md` §9). Kept as the build log for how this UI got here. The slice-at-a-time process it describes ran in the frontend's own repo; in this repo the only sanctioned changes to this app are the ones listed in `../docs/api-contract.md` §6.

> `D-NNN` ids throughout this file are entries in the frontend build's own decision log, which did not come across with the UI. The surrounding text says what each one decided; this repo's running log is `../docs/decisions.md`.

- [x] **0. Agent context setup.** `frontend/.claude/CLAUDE.md` and `frontend/.claude/DESIGN.md` — the two files that came across with the UI. The frontend repo's other context files (its own system design, rules, commands and reviewer agent) stayed there; here their job is done by `../CLAUDE.md` and `../docs/`. Done as of 2026-09-20.

No state/data-fetching library or MSW — mock mode is a per-resource swappable function instead (`src/api/customers.ts`, `decisions.ts`; D-009 superseded), one module per capability rather than a single client. No test runner or PWA plugin yet. Exit met: `npm run dev` shows the sign-in shell; `npm run build`/`npm run lint` pass.

- [x] **3. Policy creation.** New-policy flow (`src/screens/NewPolicy/`, DESIGN.md #7/#13-16): `NewPolicyShell` (shared chrome), `NewPolicyDescribe` (AI-on/off switch, folding DESIGN's #13/#14 into one screen per its own "same shell" note), `NewPolicyForm` (AI-off fields), `NewPolicyReading`, `NewPolicyTimeout`, `NewPolicyCheck` (review + dry run + confirm), orchestrated by `NewPolicyFlow`. Policy state is a new session-only `PolicyContext`/`PolicyProvider` (mirrors `CustomerContext`'s durability), keyed by `card_id`. API layer `src/api/policy.ts` implements C1 (`compilePolicy`)/C2 (`confirmPolicy`)/C3 (`getPolicy`, mock always resolves `null` — no backend to persist to, confirmation updates `PolicyContext` directly from `confirmPolicy`'s own response). AI-read mock matches by instruction *text* against `src/mocks/fixtures/policy-drafts.json` (generated by `frontend/scripts/build_policy_fixture.py`: hand-curated plain-language checks, but dry-run would-violate/would-fit/would-ask counts are computed against each scenario's own last-30 `authorization_history.csv` rows, not invented) — never by scenario id. Typing "force timeout" in the instruction box is the documented way to reach `NewPolicyTimeout` in mock mode (no real model call to time out). Exit met: each of the 5 scenario instructions (verbatim from `scenario_catalogue.csv`) compiles and confirms; the AI-off form path produces an equivalent review with no simulated delay; confirming flips Home's `PolicyCard` from Blocked to Active for the session. Not done: Manage/Revoke on `PolicyCard` render disabled (slice 5); `getPolicy`/C3 has no real read path since nothing persists past the session yet. "Applies to" was fixed/read-only at first ("every mock customer has exactly one card") — wrong for 2 of the 4 live customers, whose single visible account has a genuine second card; a real `CardPicker` was added in D-050. Home's entry point (`PolicyCard`) was later removed entirely (D-053) — Home now only shows a read-only "Active policies" list; New Policy is reached from Accounts/Card detail instead.
- [x] **4. Step-up inbox.** `src/screens/Approvals/Approvals.tsx` replaces the stub: pending attention cards (`Waiting for you` pill, `CountdownBar`, basket lines with an ochre border when `injection_flag` is set, "Why your rules are unsure" box, Approve/Reject) and an "Expired · N" section. `src/config.ts` holds `HUMAN_WINDOW_SECONDS` (120) — the one place components read the countdown length from. A pending step-up is a `Decision` with `status: 'pending_human'` and `deadline_at` set (`deadline_at` is optional on `Decision`, real-clock, computed at read time in `src/api/decisions.ts` from a small hand-curated demo-pacing map, `DEMO_SECONDS_REMAINING` — not stored in the fixture) — there is no separate `Approval` type or endpoint (C7 was proposed then folded back into C6, D-034). `src/state/DecisionsContext.tsx`/`DecisionsProvider.tsx` is the one shared store both Activity and Approvals read from: a single ticking clock moves an unanswered pending item to expired locally (`uncertain_outcome: 'expired'` as of D-041 — originally `decision: 'expired'`, since superseded), `resolve` (C8) is never called automatically, and resolving or expiring updates the one list both screens see — no more independent fetches to drift apart. `TabBar`'s approvals badge is wired to the live pending count. Exit met: each of CU0001/CU0006/CU0019's one pending step-up shows a live countdown, Approve/Reject resolves it (visible immediately in Activity too) without ever rendering "Approved" styling, and an unanswered one expires client-side without a fabricated resolve call. The `LeashMeter` "if you approve" preview DESIGN.md's card spec calls for was deferred here (no `LeashMeter` or structured per-card limits existed until slice 6) and built once they did — D-047, along with the rest of the pending card's missing facts and evidence.
- [x] **5. - [x] **8. Scenario run wiring.** Resolved (D-043): the UI never starts a run — the team/backend does it out of band, and a "scenario run" is a demo-operator mechanism the customer never sees, not something this customer-facing app needs a screen for. No new UI needed: "reflecting a run started elsewhere" is already exactly what every screen has done since slice 2 — read decisions via C6 as they arrive. Nothing to build.
- [x] **9. Demo hardening.** Error states: New Policy flow's form-submit and confirm paths had no error handling at all (uncaught rejection / silent failure) — fixed with inline messages matching the "say what's safe" pattern already used elsewhere. `CardDetail`/`DecisionDetail` no longer render a silent blank screen for a missing record. Accessibility: `OrderCapLeashMeter`'s dots were color-only — now also shaped (circle/rounded-square/diamond, reusing `OverviewHero`'s own convention) per DESIGN.md; computed WCAG contrast ratios for every muted-text-on-tint pairing in use, found and fixed one real failure (`card-icon-gray` on white, 2.16:1 — swapped to `ink-muted`, 5.26:1). PWA: manifest + icon + a deliberately no-op service worker (no caching — a hackathon demo rebuilds often, and stale cached assets would be worse than no offline support) — hand-rolled rather than `vite-plugin-pwa`, since this sandbox has no network access to verify the plugin's compatibility with this project's unusually-high Vite version. Rehearsed demo path written up in the frontend repo's own pitch notes (not carried over — this repo's is `../docs/demo-script.md`). Exit criterion run against the jury rubric: 4 of 5 criteria scored 3–4 with no hard rule violations; "skillful use of AI" scored 2 — not a frontend gap but a scope one (the AI-read path is fixture-matched in mock mode, not a live model call, because the real compiler is backend work that doesn't exist yet, per non-negotiable 6's decoupling). Pitch guidance from the review folded into the demo path (frame this honestly, lead with the injection/revoke beats instead). The literal "no criterion below 3" bar isn't met by frontend work alone — flagged to the user rather than closed out on a guess.
