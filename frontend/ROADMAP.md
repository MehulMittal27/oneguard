# Frontend roadmap

Status: **all nine slices shipped** (see `README.md` §9). Kept as the build log for how this UI got here. The slice-at-a-time process it describes ran in the frontend's own repo; in this repo the only sanctioned changes to this app are the ones listed in `../docs/api-contract.md` §6.

> `D-NNN` ids throughout this file are entries in the frontend build's own decision log, which did not come across with the UI. The surrounding text says what each one decided; this repo's running log is `../docs/decisions.md`.

- [x] **0. Agent context setup.** `frontend/.claude/CLAUDE.md` and `frontend/.claude/DESIGN.md` — the two files that came across with the UI. The frontend repo's other context files (its own system design, rules, commands and reviewer agent) stayed there; here their job is done by `../CLAUDE.md` and `../docs/`. Done as of 2026-09-20.
- [x] **1. Scaffold.** Vite + React + TypeScript (`npm create vite`). Styling: Tailwind v4, tokens mapped from `DESIGN.md` via `src/styles/tokens.css` + `src/index.css`'s `@theme`. `.env`/`.env.example` (`VITE_API_BASE_URL`, `VITE_USE_MOCKS`). No state/data-fetching library or MSW — mock mode is a per-resource swappable function instead (`src/api/customers.ts`, `decisions.ts`; D-009 superseded), one module per capability rather than a single client. No test runner or PWA plugin yet. Exit met: `npm run dev` shows the sign-in shell; `npm run build`/`npm run lint` pass.
- [x] **2. Theme, nav shell and decision feed (read-only, mocked).** Ink and signal only — Security print deliberately deferred (D-018/D-020, user instruction), token names kept portable for when it's added. Bottom tab bar (`TabBar.tsx`, Home/Accounts/Activity/Approvals, Accounts and Approvals still stubs). Decision feed built on the Activity tab (`DESIGN.md` #3): filter tiles, date-grouped `DecisionMark` rows, capability C6 (proposed endpoint, `D-024`), 15 real-data mock decisions covering all 4 decision words and the untrusted-text rule on real injected merchant text. Home's header (`DESIGN.md` #2/#10, `AccountMenu` — D-021) built ahead of the rest of this slice, from an approved mockup spec. Full decision-detail rendering (evidence rows, "what the shop tried to say") is slice 7, not this one. Home's remaining sections (`OverviewHero`, "Needs your review" — renamed from "Needs your OK" in D-049, "Latest by your control") were closed out in D-046, once `DecisionsProvider` existed to back them.
- [x] **3. Policy creation.** New-policy flow (`src/screens/NewPolicy/`, DESIGN.md #7/#13-16): `NewPolicyShell` (shared chrome), `NewPolicyDescribe` (AI-on/off switch, folding DESIGN's #13/#14 into one screen per its own "same shell" note), `NewPolicyForm` (AI-off fields), `NewPolicyReading`, `NewPolicyTimeout`, `NewPolicyCheck` (review + dry run + confirm), orchestrated by `NewPolicyFlow`. Entry point is Home's new "Policies by card" section (`PolicyCard` component) — Accounts/Card-detail don't exist until slice 6, so this also closes the loose end left by slice 2's Home docstring. Policy state is a new session-only `PolicyContext`/`PolicyProvider` (mirrors `CustomerContext`'s durability), keyed by `card_id`. API layer `src/api/policy.ts` implements C1 (`compilePolicy`)/C2 (`confirmPolicy`)/C3 (`getPolicy`, mock always resolves `null` — no backend to persist to, confirmation updates `PolicyContext` directly from `confirmPolicy`'s own response). AI-read mock matches by instruction *text* against `src/mocks/fixtures/policy-drafts.json` (generated by `frontend/scripts/build_policy_fixture.py`: hand-curated plain-language checks, but dry-run would-violate/would-fit/would-ask counts are computed against each scenario's own last-30 `authorization_history.csv` rows, not invented) — never by scenario id. Typing "force timeout" in the instruction box is the documented way to reach `NewPolicyTimeout` in mock mode (no real model call to time out). Exit met: each of the 5 scenario instructions (verbatim from `scenario_catalogue.csv`) compiles and confirms; the AI-off form path produces an equivalent review with no simulated delay; confirming flips Home's `PolicyCard` from Blocked to Active for the session. Not done: Manage/Revoke on `PolicyCard` render disabled (slice 5); `getPolicy`/C3 has no real read path since nothing persists past the session yet. "Applies to" was fixed/read-only at first ("every mock customer has exactly one card") — wrong for 2 of the 4 live customers, whose single visible account has a genuine second card; a real `CardPicker` was added in D-050. Home's entry point (`PolicyCard`) was later removed entirely (D-053) — Home now only shows a read-only "Active policies" list; New Policy is reached from Accounts/Card detail instead.
- [x] **4. Step-up inbox.** `src/screens/Approvals/Approvals.tsx` replaces the stub: pending attention cards (`Waiting for you` pill, `CountdownBar`, basket lines with an ochre border when `injection_flag` is set, "Why your rules are unsure" box, Approve/Reject) and an "Expired · N" section. `src/config.ts` holds `HUMAN_WINDOW_SECONDS` (120) — the one place components read the countdown length from. A pending step-up is a `Decision` with `status: 'pending_human'` and `deadline_at` set (`deadline_at` is optional on `Decision`, real-clock, computed at read time in `src/api/decisions.ts` from a small hand-curated demo-pacing map, `DEMO_SECONDS_REMAINING` — not stored in the fixture) — there is no separate `Approval` type or endpoint (C7 was proposed then folded back into C6, D-034). `src/state/DecisionsContext.tsx`/`DecisionsProvider.tsx` is the one shared store both Activity and Approvals read from: a single ticking clock moves an unanswered pending item to expired locally (`uncertain_outcome: 'expired'` as of D-041 — originally `decision: 'expired'`, since superseded), `resolve` (C8) is never called automatically, and resolving or expiring updates the one list both screens see — no more independent fetches to drift apart. `TabBar`'s approvals badge is wired to the live pending count. Exit met: each of CU0001/CU0006/CU0019's one pending step-up shows a live countdown, Approve/Reject resolves it (visible immediately in Activity too) without ever rendering "Approved" styling, and an unanswered one expires client-side without a fabricated resolve call. The `LeashMeter` "if you approve" preview DESIGN.md's card spec calls for was deferred here (no `LeashMeter` or structured per-card limits existed until slice 6) and built once they did — D-047, along with the rest of the pending card's missing facts and evidence.
- [x] **5. Policy management.** No DESIGN.md mockup exists for this — filled with a `BottomSheet`-based `RevokeSheet` on Home's `PolicyCard` (D-035) rather than a new full-screen flow: confirm, then the mandate is removed from `PolicyContext` (`removePolicyForCard`), reverting the card to its existing Blocked/no-policy state; never touches any pending decision on that card (platform behavior there is unspecified). `api/policy.ts` gained `revokePolicy` (C5), same mock/real branch pattern as every other resource function. A `TightenSheet` (Manage, C4 — per-order-limit reduction + the one-directional Ask-me→Block toggle) was built, tried, and pulled per user feedback (D-036) — component deleted, `PolicyCard` now shows Revoke only. `api/policy.ts`'s `tightenPolicy` and the contract's C4 endpoint are left in place, dormant, for whenever Manage gets a design worth shipping. Exit met (trivially, since there's no add/edit control of any kind): no UI control can loosen a rule or move `uncertainty_policy` back toward `approve`. `PolicyCard` and Home's `RevokeSheet` trigger were later removed (D-053) — Revoke now lives only on Card detail, which already had its own `RevokeSheet` since slice 6.
- [x] **6. Spend and Accounts.** Multi-account customers (DESIGN.md #10/#11/#12), originally deferred here (D-037), resolved later in D-057 — see that row for what shipped and what's deliberately still not built (`AccountPicker`). `src/screens/Accounts/Accounts.tsx` replaces the stub: real account/card data (`api/accounts.ts`, C10, `frontend/scripts/build_accounts_fixture.py` joining `accounts.csv`/`cards.csv`), each card row → `CardDetail.tsx` (has a policy) or the New Policy flow (doesn't). `CardDetail.tsx` (DESIGN.md #6): boxed instruction, "what your rules do" bullets, `LeashMeter`, Revoke only (D-036), card-scoped activity. `LeashMeter.tsx` has both DESIGN.md variants — the standard track for CA0001 (the only period-limit scenario) and a dot ruler (DESIGN.md's own "spec-only" fallback) for the 3 per-order-cap-only cards. `src/lib/spend.ts` computes spend client-side from the mandate's own checks + the shared `DecisionsProvider` (C9 needed no endpoint, same precedent as the policy dry-run). Bank limits are fetched but never shown on the meter (DESIGN.md: never mix the two). Added 3 more real, curated rows to `decisions.json` so CA0001 has a genuine near-limit example (CHF 254.50/300). Exit met: CA0001's track meter reads correctly near its limit; CA0011/CA0023/CA0039's dot rulers render, with CA0023 visibly near its per-order cap; a pending step-up shows as a dashed ghost, never solid.
- [x] **7. Decision detail polish.** `src/screens/DecisionDetail/DecisionDetail.tsx` (`DESIGN.md` #8/#9, generalized to all 3 decision categories, D-039, D-040, D-041): decluttered banner (D-040 — no restated reason text, real `order_returnable`/`delivery_by` facts instead), evidence rows (pass/fail/uncertain), an injection box (renders whenever `injection_flag` is set, not scenario-special-cased) showing the flagged item's shop text verbatim, a "Policy applied" section (D-041, check chips → Card detail), "Also caught on this card". Reached by tapping any `DecisionMark` row — now optionally a button — except a still-pending one, which routes to Approvals instead (D-041). No new endpoint — reuses `DecisionsProvider`'s already-loaded C6 data. DESIGN.md #8's "View policy" footer button, originally trimmed here, was built in D-041 as the "Policy applied" section. Exit met: every decision across the 4 live customers is browsable with correct banner/evidence, including the injection case (AU0037/AU0040). Screen #9's persona-specific chrome (avatar/name header, "Switch customer" back link, CTA back to that persona's Home) wasn't built at the time — `DecisionDetail` only had #8's generalized version. Added in D-058, gated on `injection_flag` rather than a new prop or scenario check.
- [x] **8. Scenario run wiring.** Resolved (D-043): the UI never starts a run — the team/backend does it out of band, and a "scenario run" is a demo-operator mechanism the customer never sees, not something this customer-facing app needs a screen for. No new UI needed: "reflecting a run started elsewhere" is already exactly what every screen has done since slice 2 — read decisions via C6 as they arrive. Nothing to build.
- [x] **9. Demo hardening.** Error states: New Policy flow's form-submit and confirm paths had no error handling at all (uncaught rejection / silent failure) — fixed with inline messages matching the "say what's safe" pattern already used elsewhere. `CardDetail`/`DecisionDetail` no longer render a silent blank screen for a missing record. Accessibility: `OrderCapLeashMeter`'s dots were color-only — now also shaped (circle/rounded-square/diamond, reusing `OverviewHero`'s own convention) per DESIGN.md; computed WCAG contrast ratios for every muted-text-on-tint pairing in use, found and fixed one real failure (`card-icon-gray` on white, 2.16:1 — swapped to `ink-muted`, 5.26:1). PWA: manifest + icon + a deliberately no-op service worker (no caching — a hackathon demo rebuilds often, and stale cached assets would be worse than no offline support) — hand-rolled rather than `vite-plugin-pwa`, since this sandbox has no network access to verify the plugin's compatibility with this project's unusually-high Vite version. Rehearsed demo path written up in the frontend repo's own pitch notes (not carried over — this repo's is `../docs/demo-script.md`). Exit criterion run against the jury rubric: 4 of 5 criteria scored 3–4 with no hard rule violations; "skillful use of AI" scored 2 — not a frontend gap but a scope one (the AI-read path is fixture-matched in mock mode, not a live model call, because the real compiler is backend work that doesn't exist yet, per non-negotiable 6's decoupling). Pitch guidance from the review folded into the demo path (frame this honestly, lead with the injection/revoke beats instead). The literal "no criterion below 3" bar isn't met by frontend work alone — flagged to the user rather than closed out on a guess.
